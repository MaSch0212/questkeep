# Decisions

Short log of choices made while building. Newest at the bottom of each section.

## Tooling

- **pnpm workspace with `minimumReleaseAge: 2880` (2 days)** instead of npm. Requested by the
  maintainer for supply-chain safety. Root `package.json` holds the Tauri CLI and aggregate
  scripts; `ui/` is the only workspace package. Dependency ranges are major-only (`^3.0.0`) so
  pnpm can pick the newest *mature* version.
- **Cargo `min-publish-age = "2 days"`** in `.cargo/config.toml`. Stabilized in Cargo 1.100; the
  local stable toolchain is 1.99, which ignores the key, so `pnpm deps:rust` runs
  `cargo +nightly update` to resolve the lockfile. Builds use stable and keep locked versions.
- **Aggregate check is a Node script** (`scripts/check.mjs`, run as `pnpm check`) rather than
  `just` or `cargo xtask`: Node is already required, it's cross-platform, and it avoids another
  tool install. CI runs the same steps individually for readable logs.
- **oxfmt 0.73 works** for TS/TSX/CSS/JSON with `--check`; no fallback needed. Generated
  bindings are excluded from formatting and linting.
- **TypeScript 7 (native `tsc`)** is used for `tsc --noEmit` only; Vite/vitest transpile on their own.
- **vite-plugin-solid HMR is disabled under vitest** (`hot: !process.env.VITEST`): solid-refresh
  breaks module resolution in jsdom tests.
- **`.gitattributes` forces LF** so rustfmt/oxfmt checks agree on Windows checkouts with
  `core.autocrlf=true`.
- **MSVC toolchain on Windows** (Visual Studio Build Tools, VC workload). The machine had none;
  installed via winget at the maintainer's request.

## Architecture

- **`ts-rs` for shared types** instead of `tauri-specta`: tauri-specta 2 is still a release
  candidate. Bindings are generated by `cargo test` into `ui/src/bindings/` and checked for drift.
- **Core is synchronous** (std threads, `ureq` for HTTP). Tauri commands run core calls on the
  async runtime's blocking pool. Avoids tying the core to tokio and keeps it simple to test.
- **`sysinfo` for process enumeration** on Windows and Linux instead of hand-written Win32
  toolhelp and `/proc` code. It provides exe paths and parent PIDs on both OSes; the `platform`
  module still owns registry access and Steam path discovery.
- **Data dir** is `dirs::data_dir()/questkeep` (`%APPDATA%\questkeep`, `~/.local/share/questkeep`)
  rather than Tauri's identifier-based dir, so core resolves it without Tauri. Portable mode via
  `portable.txt` next to the executable.
- **Asset protocol scope is granted at runtime** to the resolved images dir only, instead of a
  broad static scope in `tauri.conf.json`.

## Launching and playtime

- **Default tracking for `file` actions = process tree** (the started process and every
  descendant seen, kept after the root exits), like Playnite. I briefly also adopted processes
  from the executable's folder that started after the launch, to catch launchers that spawn the game
  detached; a live test with an exe in `System32` recorded 22 s for a 7 s run because unrelated
  system processes kept matching, so that was dropped. Launcher-style games can switch to
  `directory` tracking in their launch options.
- **URI launches (Steam) are tracked by install directory**, as in Playnite, but with a 90 s
  startup timeout (Playnite waits forever). Limits: games whose executable lives outside the
  install dir (some anti-cheat bootstrappers) may not be detected. On Linux, Proton games run as
  `wine64-preloader` from the Proton folder, so directory matching also checks each process's
  working directory and path-like command-line arguments (Wine `Z:\` paths are mapped back to
  Unix paths). Undetected games produce a "couldn't find the process" notice and no playtime.
  Steam's own playtime is not imported in v0.1.
- **Sessions are persisted** with a heartbeat every poll (2 s). App exit saves elapsed time; a
  crash is recovered on next start up to the last heartbeat (sleep gaps inside a crashed session
  are not subtracted, a deliberate simplification).
- **Launched games get null stdio** and Windows arguments are passed verbatim (`raw_arg`), so the
  user's quoting works exactly as typed in a shortcut. On Linux arguments are split shell-style.
- **`play_count` and `last_played` update when a session ends** (Playnite updates them at start),
  so a game that fails to start doesn't count as played.

## Steam and covers

- **Steam tool filtering** extends Playnite's (redist 228980, soundtracks) with Steam Linux
  Runtime / Proton / SteamVR ids and name prefixes, because those have local manifests and would
  show up as games, especially on Linux.
- **Covers come from Steam's local `appcache/librarycache` first**, then the store CDN
  (`shared.cloudflare.steamstatic.com` 600x900 assets, then the legacy akamai URL). Downloads are
  validated by magic bytes (CDNs sometimes answer 200 with HTML) and capped at 20 MB. Failed games
  are not retried within the same run. Providers expose `cover_candidates()`, so future providers
  plug into the same fetcher.
- **No landscape `header.jpg` fallback**: a 2:3 grid looks worse with letterboxed banners than with
  the placeholder tile.

## Store accounts and metadata

- **Owned games come from the provider's own API, configured per provider** in
  `settings.providers.<id>` and passed to `scan_owned()` as plain JSON, so providers (and later
  plugins) define their own settings without schema changes in the core.
- **API keys (Steam Web API, SteamGridDB) live in the system keyring**, like sign-in tokens
  (entries `setting:steam.apiKey` / `setting:steamGridDbApiKey`). `SettingsStore` strips them from
  `settings.json` on save and fills them in on load, so the UI still sees one settings object.
  Earlier versions wrote them in plain text; the first load moves them into the keyring and
  rewrites the file. Without a keyring, saving a key fails (never plain text), while existing
  plain values keep working until a keyring is available. Portable mode therefore does not carry
  keys to another machine; that is intended.
- **Store playtime is merged as the maximum**, never added: Questkeep's own tracking and the store
  usually count the same sessions, so summing would double them.
- **Metadata is fetched by one worker with at least 1.5 s between requests**: Steam's appdetails
  endpoint allows roughly 200 requests per 5 minutes. A store without data marks the game as
  checked; network errors don't, so they're retried on the next start.

## Frontend

- **Own row virtualization instead of `@tanstack/solid-virtual`.** With `@tanstack/virtual-core`
  3.19.5 the Solid adapter (3.13.47) ended up with its scroll/resize observers detached right after
  mounting, so the grid never re-rendered on scroll (found during the 5,000-game check). Grid rows
  have a fixed height, so the visible window is simple arithmetic; `ui/src/lib/virtualRows.ts`
  (unit-tested) plus a passive, rAF-throttled scroll listener replaced the dependency.
- **Search runs in SQLite**, not in the webview, so it's unit-tested with the rest of the queries
  and stays correct for Unicode case folding (`search_key` is Rust-lowercased). An 80 ms debounce
  keeps IPC calls down while typing.
- **Covers are cache-busted** with a per-game version query parameter bumped on `gamesChanged`
  events, because a cover's path stays the same when its content changes.
- **The main window is created in code** (`"create": false` in `tauri.conf.json`). Setting
  `"visible": false` in the config and hiding later was not enough: the window still showed up on
  Windows. Building it ourselves allows a dev-only hidden mode (`QUESTKEEP_HIDDEN=1`, see
  `scripts/dev-hidden.ps1`) for testing through the DevTools port without a window or focus change,
  and showing the normal window only after setup avoids a white flash.

## Releases

- **The version comes from git tags, not from a file.** The latest `vX.Y.Z` tag is the current
  version, so there is no number to bump by hand or to disagree between `Cargo.toml`,
  `tauri.conf.json` and `package.json`; the release workflow writes the computed version into
  those files for the build and commits it with the tag (`docs/RELEASING.md`).
- **Changesets are deleted in the release commit.** The pending files are the release queue: the
  commit that bumps the version also removes them, so the next run starts empty and the notes are
  never published twice. The workflow records which files it consumed (`consumed.txt`), so a
  changeset merged during the build survives for the next release; the job aborts if `main` moved.
- **Release dry run.** `dry_run` computes the version/notes and builds the installers but skips
  the commit, tag and publish, so the pipeline (and signing secrets) can be tested without
  producing a release.
- **Auto-update uses the Tauri updater plugin with GitHub Releases as the endpoint** (`latest.json`
  generated by `scripts/release/latest-json.mjs` rather than `tauri-action`, which wants to own
  the tag and release creation and does not fit the tag-from-changesets flow). The update check is
  disabled in debug builds. Updater artifacts are opt-in (`tauri.updater.conf.json`, release only)
  because `createUpdaterArtifacts` needs the private key; plain builds and CI work without it.

## Linux stores

- **Same `source` + `source_game_id` on every OS for Epic and GOG.** On Linux the `epic` provider
  reads Legendary/Heroic (`installed.json`, id = AppName) and `gog` reads Heroic's
  `gog_store/installed.json` (id = GOG product id), so a library database moved between systems
  keeps its games, playtime and favourites.
- **Heroic games launch through `heroic://launch/<runner>/<appName>`** (a `uri` action with
  `Directory` tracking on the install folder). Heroic's protocol handler accepts this path form and
  `heroic://launch?appName=..&runner=..`; the path form also works in older releases. Heroic has no
  install URI, so there is no install action. Standalone Legendary installs use
  `legendary launch <app>` (a `file` action) when the binary is on `PATH`, otherwise no action.
- **Lutris is read straight from `pga.db`** (read-only, temporary-copy fallback if locked) and
  registered on non-Windows builds only. Steam-runner games are skipped; the game `directory` is
  ignored for tracking when it is `/` or the home folder, since it would match every process.

## Artwork (SteamGridDB)

- **SteamGridDB is a fallback artwork source, keyed by a user-provided API key** kept in the
  system keyring like the Steam key (see "Store accounts and metadata"). `Library` owns the shared `SteamGridDb`
  client and `save_settings` updates its key in place, so the running fetchers pick up a new key
  without restarting and without reading settings per job. A 401/403 marks the key rejected until
  it changes, so a bad key costs one request, not one per game.
- **SteamGridDB calls share one global limiter** (at least 500 ms between requests, a
  `Mutex<Instant>` slot reservation) instead of a dedicated worker, so cover workers and the
  metadata worker can both use it while the API sees at most ~2 requests per second. Image
  downloads go to the CDN and skip the limiter.
- **"SteamGridDB had nothing" is remembered in `games.extra`** (`steamGridDbCoverCheckedAt`,
  `steamGridDbBackgroundCheckedAt`, RFC 3339) rather than a new column or migration: it is cheap,
  per image kind, and cleared by `refetch_artwork`. Network and key errors are not remembered.
- **Providers flag poor covers with `LibraryProvider::covers_are_low_quality`** (Xbox: square
  logos) rather than a per-candidate field: the quality is a property of the whole source, and a
  default method keeps other providers untouched. With a key, SteamGridDB is tried first and the
  logo is the fallback. Covers already stored are never replaced automatically (a user-picked
  cover is indistinguishable from a fetched one); `refetch_artwork` replaces on request.

## Store account sign-in (GOG, Epic)

- **Tokens only in the system keyring** (`keyring` 3.x: Windows Credential Manager, Linux Secret
  Service, macOS Keychain), service `dev.masch0212.questkeep`, user = provider id. **No plain-file
  fallback**: without a keyring (Linux without Secret Service) sign-in fails with a readable
  message instead of writing secrets next to the library. The Steam and SteamGridDB API keys
  use the same store (see "Store accounts and metadata").
  Linux uses the `sync-secret-service` backend with `crypto-rust` (no OpenSSL), which
  needs `libdbus-1-dev` + `pkg-config` to build.
- **The access token is not persisted**, only refresh token, account id and display name: the
  Windows credential blob is limited to 2560 bytes (UTF-16) and Epic's eg1 access tokens exceed it.
  After a restart the first request refreshes (one extra call); refresh tokens rotate and are saved.
- **Refresh failure semantics**: a rejected refresh token (HTTP 400/401/403) deletes the tokens and
  reports "Sign in to <Store> again in Settings." (`NotConfigured`); a network or 5xx failure keeps
  them. Signed out, owned scans are skipped silently and Epic metadata returns an error (not "no
  data") so it is retried; `sign_in_with_code` resets the "checked" marker of games without a
  description for that store.
- **The login window has no IPC access.** It loads remote store pages, so `capabilities/default.json`
  names only `main`, no remote-URL capability exists, and the invoke handler additionally rejects
  every app command whose webview is not `main` (app commands are not covered by capabilities by
  default). The window uses a private profile, allows only https navigations, and the code is
  taken by cancelling the redirect (GOG: `on_login_success?code=`; Epic: a script on the
  `api/redirect` JSON page navigates to `https://questkeep.invalid/epic-auth?code=`).
- **Public client ids are embedded**: the GOG Galaxy and Epic launcher OAuth clients that
  open-source launchers (Heroic/gogdl, Legendary, Playnite) use. They identify the client app, not
  the user. Only URLs, parameter and field names were taken from the GPL projects, no code.
- **Paste-a-code fallback** (`sign_in_with_code`) exists for both stores in case the embedded login
  fails (captcha, webview problems): GOG accepts the code or the whole redirect address, Epic the
  `authorizationCode` value or the page JSON.
- **Epic catalog data is cached in memory per run** and fetched in namespace batches of up to 40
  items per request; covers (`DieselGameBoxTall`), backgrounds (`DieselGameBox`, `OfferImageWide`)
  and metadata reuse it. A disk cache is a follow-up.
- **Epic artwork works without an account.** The installed manifests (and Legendary's
  `metadata/<app>.json`) carry namespace + catalog item id; the catalog `bulk/items` endpoint accepts
  an app-only token from the launcher's public client (`client_credentials`, verified live), so no
  user token or store GraphQL scraping is needed. The token stays in memory, answers are cached for
  the run, and a signed-in account is still tried first. Covers are only tall art
  (`DieselGameBoxTall`, `OfferImageTall`); wide-only listings give no cover, so SteamGridDB or the
  placeholder is used instead of cropping wide art.
- **The Epic login window uses the normal WebView user agent.** With Playnite's
  `EpicGamesLauncher` user agent, Epic treats the window as its launcher and rejects our redirect
  URL ("Redirect URL is not known to the client"). Without it, the standard login page redirects
  to the code page. The launcher-style `localhost/launcher/authorized?code=` redirect is still
  caught in case Epic sends it.
- **Install actions open the store's install dialog.** Steam `steam://install/<id>`, GOG Galaxy
  `goggalaxy://installationScreen/<id>` (Galaxy also handles `installGame`, `openGameView`,
  `launchGame`), Epic `com.epicgames.launcher://apps/<namespace>%3A<itemId>%3A<appName>?action=install`
  with the ids from the signed-in library; the bare appName form only opens the launcher.
- **Uninstall always delegates to the store, behind a UI confirm step.** Steam
  `steam://uninstall/<id>` (same as Playnite). The Epic launcher and Galaxy have no known
  uninstall URI (Galaxy's protocol commands are launch/install/focus/view only), so Epic opens
  `com.epicgames.launcher://store/library` and GOG runs the game's own `unins000.exe` from the
  registry install path (both as Playnite does). Xbox opens `ms-settings:appsfeatures`. Heroic and
  Lutris have no documented uninstall protocol, so no button there. Provider-level
  `can_uninstall` (not per game) keeps `ProviderInfo` the only thing the UI needs; per-game
  failures (missing uninstaller) come back as readable errors. No DB write: the next scan flips
  `installed`.


## Tray and autostart

- **Hiding to the tray destroys the main window** rather than hiding it: a hidden WebView2 window
  keeps its renderer (150-250 MB); recreating it takes well under a second and the UI reloads its
  state from the core. The cost is that UI-only state (scroll position, open details) resets.
- **A flag, not window counting, keeps the process alive**: `ExitRequested(code = None)` is
  prevented only while `hidden_to_tray` is set and no tray Exit happened. Closing the window with
  "close to tray" off still quits as before.
- **Tray unavailable means the close button quits**: hiding with no way back would strand the app.
- **Single instance in release builds only**: debug builds skip `tauri-plugin-single-instance` so a
  dev or throwaway instance can run next to an installed one. A second start with `--minimized`
  (autostart racing a manual start) does not raise the window.
- **Autostart runs `--minimized`** and `startMinimized` decides whether that hides the window, so
  the toggle can change without rewriting the registry entry. The entry is written before the
  setting is saved (a refusal is shown and nothing is saved), and refreshed at startup in release
  builds so an updated install path stays correct. Debug builds never touch it.
- **Open folder goes through Rust** (`open_app_folder`) instead of widening `opener` ACL scopes to
  the data directory, which is user-specific and can be portable.
- **Menu rebuilds are debounced (2 s) and skipped when the model is unchanged**, because cover and
  metadata downloads emit `GamesChanged` continuously during the first scan.
- **Tray game icons are made once and cached as 32x32 PNGs, never during a menu build.** A menu
  build then only decodes at most 40 tiny files; producing icons (downloads, exe extraction,
  resizing) happens on the metadata worker and is announced by `GamesChanged`. 32 px stays sharp at
  150-200 % scaling. Items without an icon are plain text items (no placeholder box).
- **Icon sources, best first: store icon, executable icon, cover crop.** The store icon is the
  intended artwork and is free for Steam (local librarycache). The executable icon is what the
  game shows in Explorer, so it beats a cropped box art for `file` games (manual, GOG, Lutris). The
  cover crop (top-aligned: the key art sits at the top of 2:3 covers) is the universal fallback.
  Provider icons must be nearly square, because Epic has no real icon (`Thumbnail` is used when
  square) and a squashed wide logo looks worse than the fallback.
- **Steam icons have no CDN fallback**: the icon's file name is a hash only the client knows.
- **No SteamGridDB for icons**: it would add rate-limited requests for 30 small images; the
  fallbacks are good enough.
- **`image` with only png/jpeg/ico** instead of hand-written decoding/resizing: Lanczos3 resampling
  and robust decoders are not worth re-implementing, and the features keep the dependency small
  (no WebP/GIF/AVIF; those sources fall through to the next one).
- **Events go to the `main` window only** (`emit_to`), so the login windows never receive them.
- **Monochrome tray glyph following the taskbar theme** (`SystemUsesLightTheme`, not the app
  theme): white on dark taskbars, black on light ones, no tile so it fills the tray slot. A thread
  blocks in `RegNotifyChangeKeyValue` to swap it; one of the few `unsafe` modules (scoped
  `allow(unsafe_code)` in `tray_theme.rs`), because winreg cannot wait for changes and polling
  would wake the idle tray process.
- **Window placement in `window.json` in the data folder**, not via `tauri-plugin-window-state`,
  which saves to the app config dir and so would break portable mode. The last normal rectangle is
  tracked on move/resize (a minimized window reports an off-screen position) and saved before the
  window is destroyed or the app exits; it is used only if enough of the title bar is still on a
  connected monitor.
- **Custom tray popup instead of the context menu on Windows.** Native menus cannot be padded,
  show icons only at 16-20 px (scaled with nearest neighbor, so they alias) and cannot show cover
  art. A webview popup would cost 100+ MB and a cold start per opening, so the popup is plain Win32
  + Direct2D (`windows` crate, already in the lockfile through Tauri): instant, and nothing exists
  while it is closed. It is the third place with `unsafe` code (`tray_popup/{render,window}.rs`, scoped
  `allow`); layout and navigation are pure Rust with tests. Its colors mirror `theme.css` (dark
  only, like the app). No acrylic backdrop. Linux keeps the native menu (AppIndicator menus cannot be replaced there).
- **Tray popup accessibility through AccessKit** (MIT/Apache, `accesskit_windows` -> UI
  Automation), not a hand-written UIA provider: the tree is built from the same `Layout` the
  renderer draws (`tray_popup/a11y.rs`, platform independent), so a later Linux popup could expose
  it through `accesskit_unix` (AT-SPI) unchanged. Considered and rejected: a webview popup (best
  accessibility, but 100+ MB and a cold start per opening), egui (GPU context, restyling) and Slint
  (licence needs attribution). A Linux popup is blocked less by drawing than by the tray: the
  AppIndicator backend reports no clicks (tray-icon's KSNI backend would) and Wayland apps cannot
  place a window next to the tray.

- **Provider settings reach providers through `LibraryProvider::configure`**, called with
  `providers.<id>` before every scan (scans already store play actions). First user: GOG's
  `launchThroughGalaxy` (default off: direct launch also works for offline-installer games); the
  UI rescans GOG after the toggle changes so existing games switch immediately.
- **Icons cut from a cover follow the cover**: such icons are marked (`extra.iconFromCover`) and
  dropped when the cover is replaced (manually or by a SteamGridDB re-fetch); the tray queues a new
  one. Store and executable icons are kept. A finished icon job leaves the "already queued" set, so
  a dropped icon can be made again in the same run.
- **A second start of a different executable is announced** in the running instance (toast via a
  queued notice, `take_notices`): with close-to-tray on, an old build waiting in the tray otherwise
  silently swallows starts of a newer build.
