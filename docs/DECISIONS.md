# Decisions

Short log of choices made while building. Newest at the bottom of each section.

## Tooling

- **pnpm workspace with `minimumReleaseAge: 2880` (2 days)** instead of npm. Requested by the
  maintainer for supply-chain safety. Root `package.json` holds the Tauri CLI and aggregate
  scripts; `ui/` is the only workspace package. Dependency ranges are major-only (`^3.0.0`) so
  pnpm can pick the newest *mature* version.
- **Cargo `min-publish-age = "2 days"`** in `.cargo/config.toml`. Stabilized in Cargo 1.100; the
  local stable toolchain is 1.99, which ignores the key, so `pnpm deps:rust` runs
  `cargo +nightly update` to resolve the lockfile. Builds use stable and keep locked versions.
- **Aggregate check is a Node script** (`scripts/check.mjs`, run as `pnpm check`) rather than
  `just` or `cargo xtask`: Node is already required, it's cross-platform, and it avoids another
  tool install. CI runs the same steps individually for readable logs.
- **oxfmt 0.73 works** for TS/TSX/CSS/JSON with `--check`; no fallback needed. Generated
  bindings are excluded from formatting and linting.
- **TypeScript 7 (native `tsc`)** is used for `tsc --noEmit` only; Vite/vitest transpile on their own.
- **vite-plugin-solid HMR is disabled under vitest** (`hot: !process.env.VITEST`): solid-refresh
  breaks module resolution in jsdom tests.
- **`.gitattributes` forces LF** so rustfmt/oxfmt checks agree on Windows checkouts with
  `core.autocrlf=true`.
- **MSVC toolchain on Windows** (Visual Studio Build Tools, VC workload). The machine had none;
  installed via winget at the maintainer's request.

## Architecture

- **`ts-rs` for shared types** instead of `tauri-specta`: tauri-specta 2 is still a release
  candidate. Bindings are generated by `cargo test` into `ui/src/bindings/` and checked for drift.
- **Core is synchronous** (std threads, `ureq` for HTTP). Tauri commands run core calls on the
  async runtime's blocking pool. Avoids tying the core to tokio and keeps it simple to test.
- **`sysinfo` for process enumeration** on Windows and Linux instead of hand-written Win32
  toolhelp and `/proc` code. It provides exe paths and parent PIDs on both OSes; the `platform`
  module still owns registry access and Steam path discovery.
- **Data dir** is `dirs::data_dir()/questkeep` (`%APPDATA%\questkeep`, `~/.local/share/questkeep`)
  rather than Tauri's identifier-based dir, so core resolves it without Tauri. Portable mode via
  `portable.txt` next to the executable.
- **Asset protocol scope is granted at runtime** to the resolved images dir only, instead of a
  broad static scope in `tauri.conf.json`.

## Launching and playtime

- **Default tracking for `file` actions = process tree** (the started process and every
  descendant seen, kept after the root exits), like Playnite. I briefly also adopted processes
  from the executable's folder that started after the launch, to catch launchers that spawn the game
  detached; a live test with an exe in `System32` recorded 22 s for a 7 s run because unrelated
  system processes kept matching, so that was dropped. Launcher-style games can switch to
  `directory` tracking in their launch options.
- **URI launches (Steam) are tracked by install directory**, as in Playnite, but with a 90 s
  startup timeout (Playnite waits forever). Limits: games whose executable lives outside the
  install dir (some anti-cheat bootstrappers) may not be detected. On Linux, Proton games run as
  `wine64-preloader` from the Proton folder, so directory matching also checks each process's
  working directory and path-like command-line arguments (Wine `Z:\` paths are mapped back to
  Unix paths). Undetected games produce a "couldn't find the process" notice and no playtime.
  Steam's own playtime is not imported in v0.1.
- **Sessions are persisted** with a heartbeat every poll (2 s). App exit saves elapsed time; a
  crash is recovered on next start up to the last heartbeat (sleep gaps inside a crashed session
  are not subtracted, a deliberate simplification).
- **Launched games get null stdio** and Windows arguments are passed verbatim (`raw_arg`), so the
  user's quoting works exactly as typed in a shortcut. On Linux arguments are split shell-style.
- **`play_count` and `last_played` update when a session ends** (Playnite updates them at start),
  so a game that fails to start doesn't count as played.

## Steam and covers

- **Steam tool filtering** extends Playnite's (redist 228980, soundtracks) with Steam Linux
  Runtime / Proton / SteamVR ids and name prefixes, because those have local manifests and would
  show up as games, especially on Linux.
- **Covers come from Steam's local `appcache/librarycache` first**, then the store CDN
  (`shared.cloudflare.steamstatic.com` 600x900 assets, then the legacy akamai URL). Downloads are
  validated by magic bytes (CDNs sometimes answer 200 with HTML) and capped at 20 MB. Failed games
  are not retried within the same run. Providers expose `cover_candidates()`, so future providers
  plug into the same fetcher.
- **No landscape `header.jpg` fallback**: a 2:3 grid looks worse with letterboxed banners than with
  the placeholder tile.

## Store accounts and metadata

- **Owned games come from the provider's own API, configured per provider** in
  `settings.providers.<id>` and passed to `scan_owned()` as plain JSON, so providers (and later
  plugins) define their own settings without schema changes in the core.
- **API keys (Steam Web API, SteamGridDB) live in the system keyring**, like sign-in tokens
  (entries `setting:steam.apiKey` / `setting:steamGridDbApiKey`). `SettingsStore` strips them from
  `settings.json` on save and fills them in on load, so the UI still sees one settings object.
  Earlier versions wrote them in plain text; the first load moves them into the keyring and
  rewrites the file. Without a keyring, saving a key fails (never plain text), while existing
  plain values keep working until a keyring is available. Portable mode therefore does not carry
  keys to another machine; that is intended.
- **Store playtime is merged as the maximum**, never added: Questkeep's own tracking and the store
  usually count the same sessions, so summing would double them.
- **Metadata is fetched by one worker with at least 1.5 s between requests**: Steam's appdetails
  endpoint allows roughly 200 requests per 5 minutes. A store without data marks the game as
  checked; network errors don't, so they're retried on the next start.

## Frontend

- **Own row virtualization instead of `@tanstack/solid-virtual`.** With `@tanstack/virtual-core`
  3.19.5 the Solid adapter (3.13.47) ended up with its scroll/resize observers detached right after
  mounting, so the grid never re-rendered on scroll (found during the 5,000-game check). Grid rows
  have a fixed height, so the visible window is simple arithmetic; `ui/src/lib/virtualRows.ts`
  (unit-tested) plus a passive, rAF-throttled scroll listener replaced the dependency.
- **Search runs in SQLite**, not in the webview, so it's unit-tested with the rest of the queries
  and stays correct for Unicode case folding (`search_key` is Rust-lowercased). An 80 ms debounce
  keeps IPC calls down while typing.
- **Covers are cache-busted** with a per-game version query parameter bumped on `gamesChanged`
  events, because a cover's path stays the same when its content changes.
- **The main window is created in code** (`"create": false` in `tauri.conf.json`). Setting
  `"visible": false` in the config and hiding later was not enough: the window still showed up on
  Windows. Building it ourselves allows a dev-only hidden mode (`QUESTKEEP_HIDDEN=1`, see
  `scripts/dev-hidden.ps1`) for testing through the DevTools port without a window or focus change,
  and showing the normal window only after setup avoids a white flash.
- **Store logos from Simple Icons (CC0)**; Xbox, Amazon and the manual-game folder come from Font
  Awesome Free (CC BY 4.0) because Simple Icons removed Xbox and Amazon. Each provider ships its
  logo (see "Each provider ships its own logo" below).
- **Quick actions are tabbable only on the selected tile or row**, so Tab doesn't walk thousands
  of buttons. Enter still opens details; Ctrl+Enter / F5 stay the keyboard way to play or install.
  Install is offered when the game has a store id (`ProviderInfo` has no `canInstall`). In the list
  the button sits in the name column, so it never covers data.
- **Details view**: selection is separate from "details open", so switching back to grid or list
  doesn't pop the side panel. The page reuses `DetailsPanel` (`variant="page"`); its CSS uses two
  classes because the general `.details` rules come later in the file (the first version was
  squeezed to the panel width in wide windows, which only the hidden-app screenshot showed).
- **One sync status instead of a toast per store**: the core announces `scansQueued` (a full sync's
  stores, so it isn't "done" between two scans), `scanStarted`, `libraryScanned`, `scanFailed`. A
  run ends 1.5 s after no store is waiting or running, so Settings rescans and sign-in scans join
  one run; then one toast sums it up.

## Releases

- **The version comes from git tags, not from a file.** The latest `vX.Y.Z` tag is the current
  version, so there is no number to bump by hand or to disagree between `Cargo.toml`,
  `tauri.conf.json` and `package.json`; the release workflow writes the computed version into
  those files for the build and commits it with the tag (`docs/RELEASING.md`).
- **Changesets are deleted in the release commit.** The pending files are the release queue: the
  commit that bumps the version also removes them, so the next run starts empty and the notes are
  never published twice. The workflow records which files it consumed (`consumed.txt`), so a
  changeset merged during the build survives for the next release; the job aborts if `main` moved.
- **Release dry run.** `dry_run` computes the version/notes and builds the installers but skips
  the commit, tag and publish, so the pipeline (and signing secrets) can be tested without
  producing a release.
- **Auto-update uses the Tauri updater plugin with GitHub Releases as the endpoint** (`latest.json`
  generated by `scripts/release/latest-json.mjs` rather than `tauri-action`, which wants to own
  the tag and release creation and does not fit the tag-from-changesets flow). The update check is
  disabled in debug builds. Updater artifacts are opt-in (`tauri.updater.conf.json`, release only)
  because `createUpdaterArtifacts` needs the private key; plain builds and CI work without it.

## Linux stores

- **Same `source` + `source_game_id` on every OS for Epic and GOG.** On Linux the `epic` provider
  reads Legendary/Heroic (`installed.json`, id = AppName) and `gog` reads Heroic's
  `gog_store/installed.json` (id = GOG product id), so a library database moved between systems
  keeps its games, playtime and favourites.
- **Heroic games launch through `heroic://launch/<runner>/<appName>`** (a `uri` action with
  `Directory` tracking on the install folder). Heroic's protocol handler accepts this path form and
  `heroic://launch?appName=..&runner=..`; the path form also works in older releases. Heroic has no
  install URI, so there is no install action. Standalone Legendary installs use
  `legendary launch <app>` (a `file` action) when the binary is on `PATH`, otherwise no action.
- **Lutris is read straight from `pga.db`** (read-only, temporary-copy fallback if locked) and
  registered on non-Windows builds only. Steam-runner games are skipped; the game `directory` is
  ignored for tracking when it is `/` or the home folder, since it would match every process.
- **Amazon Games through Heroic's Nile runner** as provider `amazon` (non-Windows): installed games
  from `nile_config/nile/installed.json` (`{id, version, path}`), owned ones from
  `store_cache/nile_library.json` (`library`) and Nile's own `library.json`; id = Amazon product id
  (`product.id`), so a later Windows Amazon provider can share it. Launch `heroic://launch/nile/<id>`.
  Heroic's `art_cover` is a background or icon, so `covers_are_low_quality` is `true`.
- **Heroic sideloaded apps are their own provider `heroic`** ("Heroic (sideloaded)"):
  they belong to no store and Heroic gives them random ids. `sideload_apps/library.json`
  (`games`), launched via `heroic://launch/sideload/<app_name>`; browser and Mac apps are skipped.
- **Owned games without sign-in on Linux**: Epic and GOG add the libraries Heroic cached
  (`store_cache/legendary_library.json` key `library`, `gog_library.json` key `games`) and Lutris's
  `service_games` of the `egs` / `gog` services (their `appid` is the AppName / product id) to the
  account's owned list (`heroic::owned_with_local`: the account wins, local entries fill gaps, a
  signed-out or failing account still gives the local list). Lutris's own owned scan lists only
  services no provider covers (`<service>:<appid>`, no action; Steam, Epic, GOG and Amazon are
  skipped). Shapes come from Heroic's and Lutris's public source (2026-10-25); the Nile file shapes
  and Lutris service names other than `egs`, `gog`, `steam` were not seen on a real machine.

## Artwork (SteamGridDB)

- **SteamGridDB is a fallback artwork source, keyed by a user-provided API key** kept in the
  system keyring like the Steam key (see "Store accounts and metadata"). `Library` owns the shared `SteamGridDb`
  client and `save_settings` updates its key in place, so the running fetchers pick up a new key
  without restarting and without reading settings per job. A 401/403 marks the key rejected until
  it changes, so a bad key costs one request, not one per game.
- **SteamGridDB calls share one global limiter** (at least 500 ms between requests, a
  `Mutex<Instant>` slot reservation) instead of a dedicated worker, so cover workers and the
  metadata worker can both use it while the API sees at most ~2 requests per second. Image
  downloads go to the CDN and skip the limiter.
- **"SteamGridDB had nothing" is remembered in `games.extra`** (`steamGridDbCoverCheckedAt`,
  `steamGridDbBackgroundCheckedAt`, RFC 3339) rather than a new column or migration: it is cheap,
  per image kind, and cleared by `refetch_artwork`. Network and key errors are not remembered.
- **Providers flag poor covers with `LibraryProvider::covers_are_low_quality`** (Xbox used it for
  square logos until it got Store posters, see "Xbox covers and sign-in") rather than a per-candidate field: the quality is a property of the whole source, and a
  default method keeps other providers untouched. With a key, SteamGridDB is tried first and the
  logo is the fallback. Covers already stored are never replaced automatically (a user-picked
  cover is indistinguishable from a fetched one); `refetch_artwork` replaces on request.

## Metadata (IGDB)

- **IGDB is a fallback metadata source built like SteamGridDB**: `Library` owns one shared
  `Igdb` client, `save_settings` updates its credentials in place, and a 401/403 (or a refused
  token request) marks them rejected until they change. Twitch Client ID and Secret both live in the
  keyring (`setting:igdbClientId`, `setting:igdbClientSecret`); the id isn't secret, but one
  mechanism was simpler. The app token (`client_credentials`) stays in memory and is renewed on
  expiry or a 401; the secret goes in the form body, never the URL.
- **Asked only for what the store lacks**: games without a description or without genres
  (manual games, unregistered providers, `metadata()` = `Ok(None)` such as Lutris, and Epic, whose
  catalog has no genres). Only empty fields are filled, so store data and user edits are never
  overwritten. Jobs for games whose store was already asked carry no store id, so only IGDB is
  asked. Manual games are enqueued only when IGDB is configured. Verified live 2026-10-25 with
  the maintainer's credentials (a manual "Minecraft" got description and genres).
- **Exact normalized name match only** (lowercase alphanumerics, `&` = "and", leading "the"
  dropped; release year breaks ties): a wrong description is worse than none. Misses are remembered
  in `games.extra.igdbCheckedAt` (cleared by a metadata refresh); network and credential errors
  are not.
- **One global limiter, ≥ 300 ms between IGDB requests** (IGDB allows 4/s), separate from the
  1.5 s store interval so a store miss followed by IGDB doesn't wait twice. Not verified against
  the live API (no credentials during development).

## Store account sign-in (GOG, Epic)

- **Tokens only in the system keyring** (`keyring` 3.x: Windows Credential Manager, Linux Secret
  Service, macOS Keychain), service `dev.masch0212.questkeep`, user = provider id. **No plain-file
  fallback**: without a keyring (Linux without Secret Service) sign-in fails with a readable
  message instead of writing secrets next to the library. The Steam and SteamGridDB API keys
  use the same store (see "Store accounts and metadata").
  Linux uses the `sync-secret-service` backend with `crypto-rust` (no OpenSSL), which
  needs `libdbus-1-dev` + `pkg-config` to build.
- **The access token is not persisted**, only refresh token, account id and display name: the
  Windows credential blob is limited to 2560 bytes (UTF-16) and Epic's eg1 access tokens exceed it.
  After a restart the first request refreshes (one extra call); refresh tokens rotate and are saved.
- **Refresh failure semantics**: a rejected refresh token (HTTP 400/401/403) deletes the tokens and
  reports "Sign in to <Store> again in Settings." (`NotConfigured`); a network or 5xx failure keeps
  them. Signed out, owned scans are skipped silently and Epic metadata returns an error (not "no
  data") so it is retried; `sign_in_with_code` resets the "checked" marker of games without a
  description for that store.
- **The login window has no IPC access.** It loads remote store pages, so `capabilities/default.json`
  names only `main`, no remote-URL capability exists, and the invoke handler additionally rejects
  every app command whose webview is not `main` (app commands are not covered by capabilities by
  default). The window uses a private profile, allows only https navigations, and the code is
  taken by cancelling the redirect (GOG: `on_login_success?code=`; Epic: a script on the
  `api/redirect` JSON page navigates to `https://questkeep.invalid/epic-auth?code=`).
- **Public client ids are embedded**: the GOG Galaxy and Epic launcher OAuth clients that
  open-source launchers (Heroic/gogdl, Legendary, Playnite) use. They identify the client app, not
  the user. Only URLs, parameter and field names were taken from the GPL projects, no code.
- **Paste-a-code fallback** (`sign_in_with_code`) exists for both stores in case the embedded login
  fails (captcha, webview problems): GOG accepts the code or the whole redirect address, Epic the
  `authorizationCode` value or the page JSON.
- **Epic catalog data is cached in memory per run** and fetched in namespace batches of up to 40
  items per request; covers (`DieselGameBoxTall`), backgrounds (`DieselGameBox`, `OfferImageWide`)
  and metadata reuse it.
- **The Epic catalog is also cached on disk**, one JSON file per catalog item below
  `<data>/cache/epic-catalog` (public token) and `epic-catalog-account` (signed in; the two tokens
  may see different items, so one's "unknown" must not hide an item from the other). Items stay
  fresh for 7 days, "unknown item" for 1 day; corrupt, expired or future-dated files are misses;
  writes are temp file + rename and I/O errors are only logged. `ProviderRegistry::with_builtin`
  takes the cache dir (`DataPaths::cache_dir`).
- **No Epic genres.** Checked live 2026-10-25: `bulk/items` has only structural categories
  (`games`, `applications`, `addons`, ...) across 120+ namespaces and no genre attributes; the
  public store product page has feature tags only (`CO_OP`, `SINGLE_PLAYER`). Named genres exist
  only in the store GraphQL, which sits behind a Cloudflare challenge we don't work around.
  `metadata()` would read `genre/<name>` categories if Epic ever adds them.
- **Epic artwork works without an account.** The installed manifests (and Legendary's
  `metadata/<app>.json`) carry namespace + catalog item id; the catalog `bulk/items` endpoint accepts
  an app-only token from the launcher's public client (`client_credentials`, verified live), so no
  user token or store GraphQL scraping is needed. The token stays in memory, answers are cached for
  the run, and a signed-in account is still tried first. Covers are only tall art
  (`DieselGameBoxTall`, `OfferImageTall`); wide-only listings give no cover, so SteamGridDB or the
  placeholder is used instead of cropping wide art.
- **The Epic login window uses the normal WebView user agent.** With Playnite's
  `EpicGamesLauncher` user agent, Epic treats the window as its launcher and rejects our redirect
  URL ("Redirect URL is not known to the client"). Without it, the standard login page redirects
  to the code page. The launcher-style `localhost/launcher/authorized?code=` redirect is still
  caught in case Epic sends it.
- **Install actions open the store's install dialog.** Steam `steam://install/<id>`, GOG Galaxy
  `goggalaxy://installationScreen/<id>` (Galaxy also handles `installGame`, `openGameView`,
  `launchGame`), Epic `com.epicgames.launcher://apps/<namespace>%3A<itemId>%3A<appName>?action=install`
  with the ids from the signed-in library; the bare appName form only opens the launcher.
- **Uninstall always delegates to the store, behind a UI confirm step.** Steam
  `steam://uninstall/<id>` (same as Playnite). The Epic launcher and Galaxy have no known
  uninstall URI (Galaxy's protocol commands are launch/install/focus/view only), so Epic opens
  `com.epicgames.launcher://store/library` and GOG runs the game's own `unins000.exe` from the
  registry install path (both as Playnite does). Xbox opens `ms-settings:appsfeatures`. Heroic and
  Lutris have no documented uninstall protocol, so no button there. Provider-level
  `can_uninstall` (not per game) keeps `ProviderInfo` the only thing the UI needs; per-game
  failures (missing uninstaller) come back as readable errors. No DB write: the next scan flips
  `installed`.
- **Epic per-game uninstall only for standalone Legendary** (`legendary uninstall <app> -y`, the
  store tool deleting its own install; Questkeep already asked). No per-game launcher URI was found
  (web search and the launcher's files, 2026-10-25), so the Windows launcher still opens its
  library. Heroic-managed games have no action. The app name is checked (`[A-Za-z0-9_.-]`, no
  leading `-`) because it goes on a command line.
- **GOG reads `Uninstall\<productId>_is1` too** (HKLM and HKCU, native and WOW6432Node), for
  installs missing from `GOG.com\Games` and as the uninstaller (`UninstallString`, arguments kept;
  `unins000.exe` in the folder is the fallback). Only numeric key names count (Inno Setup apps use
  `_is1` as well). DLCs share the game's folder with their own `unins00N.exe`
  (Cyberpunk 2077 + Phantom Liberty + REDmod on the maintainer's PC), so records whose
  `goggame-<id>.info` `rootGameId` differs, or with `dependsOn`, are neither games nor uninstallable.
- **GOG covers: gamesdb `vertical_cover` first** (`https://gamesdb.gog.com/platforms/gog/external_releases/<id>`,
  `game.vertical_cover.url_format` with `{formatter}` empty and `{ext}` `jpg`: a 2:3 image; checked
  anonymously 2026-10-25), then the v2 `boxArtImage` (342x482). Cached per id in memory.
- **GOG playtime comes from GOG Galaxy's local database**, not the web. Playnite reads
  `/u/<username>/games/stats` with web-session cookies; `embed.gog.com/u/<username>/games/stats`
  answered 403 to the Galaxy bearer token in a live signed-in scan (2026-10-25). Galaxy itself keeps
  `%ProgramData%\GOG.com\Galaxy\storage\galaxy-2.0.db` with `GameTimes(userId, releaseKey,
  minutesInGame)` and `LastPlayedDates(userId, gameReleaseKey, lastPlayedDate)`, release keys
  `gog_<product id>` (checked on the maintainer's PC: 160 GOG rows, plus rows for other stores,
  which are ignored). Dates have no zone and are read as UTC (unverified). Applied to installed
  and owned games; no Galaxy (or Linux) means no GOG playtime.
- **Other programs' SQLite databases are read through `providers::sqlite::read_foreign`**:
  read-only first, then a temporary copy that includes the `-wal` file (Galaxy's recent changes
  live there until it checkpoints). Lutris uses the same helper.

## Xbox covers and sign-in

- **Covers, backgrounds and metadata come from the public Store display catalog, no account.**
  `GET https://displaycatalog.mp.microsoft.com/v7.0/products/lookup?alternateId=PackageFamilyName&value=<pfn>&market=US&languages=en-us&fieldsTemplate=details`
  returns the product for an installed or owned package directly (the `bigIds` form of
  `/v7.0/products` returns the same shape but needs the 12-char Store id, which the manifest does
  not carry; the PFN lookup avoids that step). Unknown packages answer 200 with `Products: []`.
  Checked live and anonymously on 2026-10-18 with Halo Infinite (`Microsoft.254428597CFE2_8wekyb3d8bbwe`,
  Store id `9PP5G1F0C2B6`). Fields used: `LocalizedProperties[0].Images[]` (`Poster` 1440x2160,
  `SuperHeroArt`, `TitledHeroArt`, `Screenshot`; `//` URIs get `https:`), `ProductTitle`,
  `DeveloperName`, `PublisherName`, `ProductDescription`, `MarketProperties[].OriginalReleaseDate`
  (dates before 1970 are placeholders and dropped), `Properties.Categories`/`Category` as genres.
  Answers (also "unknown") are cached in memory per run, one request per game for covers,
  backgrounds and metadata together; failures are not cached.
- **Cover choice**: `Poster`, then `BoxArt` only when its aspect ratio is within 0.06 of 2:3 (it is
  usually square, 1080x1080, and is skipped); `BrandedKeyArt` (0.73) is not used. The package logo
  stays as the last candidate for installed games. Background: `SuperHeroArt`, `TitledHeroArt`, the
  first `Screenshot`.
- **`covers_are_low_quality(source_game_id)` is per game**: Xbox answers `true` only when the
  Store catalog has no poster for that game (its cached answer, so no extra request); then
  SteamGridDB goes first and the square package logo is the fallback. Posters still beat
  SteamGridDB.
- **"Don't import Game Pass games" (`providers.xbox.hideGamePass`) uses the public PC Game Pass
  list**, `https://catalog.gamepass.com/sigls/v2?id=fdd9e2a7-0fee-49f6-ad69-4354098401ff&language=en-us&market=US`
  (checked anonymously 2026-10-25: a header object, then ~515 `{"id": "<Store id>"}`), compared
  with each owned title's catalog `ProductId`. The title history can't tell a purchase from a Game
  Pass play, and the entitlement (collections) API needs another token audience we couldn't verify,
  so bought games that are also in Game Pass are left out too while not installed. The documented
  entitlement API (`collections.mp.microsoft.com/v9.0/collections/publisherQuery`, Game Pass =
  `acquisitionType: Recurring`) is a service-to-service API for a title's publisher (Azure AD
  auth; unauthorized callers see `Single`), so a launcher can't use it. Installed games
  are always kept. A failing list keeps everything. Games already imported stay, because scans
  never delete games.
- **Sign-in is the Microsoft account OAuth flow Playnite's Xbox library uses** (facts only, no code
  copied). Public client id `38cd2fa8-66fd-4760-afb2-405eb65d5b0c`, scope `Xboxlive.signin
  Xboxlive.offline_access`, redirect `https://login.live.com/oauth20_desktop.srf`:
  1. `https://login.live.com/oauth20_authorize.srf?client_id=...&response_type=code&approval_prompt=auto&scope=...&redirect_uri=...`
     (login window; the shell cancels the redirect to `oauth20_desktop.srf?code=` and takes the code).
  2. `POST https://login.live.com/oauth20_token.srf` (form: `grant_type` `authorization_code` or
     `refresh_token`, `code`/`refresh_token`, `scope`, `client_id`, `redirect_uri`) gives the Microsoft
     access and refresh tokens. Only the refresh token is persisted (keyring), like Epic and GOG.
  3. `POST https://user.auth.xboxlive.com/user/authenticate` (JSON, `x-xbl-contract-version: 1`,
     `RelyingParty http://auth.xboxlive.com`, `AuthMethod RPS`, `SiteName user.auth.xboxlive.com`,
     `RpsTicket d=<MS access token>`) gives the Xbox user token.
  4. `POST https://xsts.auth.xboxlive.com/xsts/authorize` (JSON, `RelyingParty http://xboxlive.com`,
     `SandboxId RETAIL`, `UserTokens [<user token>]`) gives the XSTS token with the claims `uhs`
     (user hash), `xid` (XUID) and `gtg` (gamertag, shown as the account name). A 401 carries
     `XErr` (no Xbox profile 2148916233, region 2148916235, adult verification 2148916236/7,
     child account 2148916238); these become readable messages.
  5. `GET https://titlehub.xboxlive.com/users/xuid(<xuid>)/titles/titlehistory/decoration/detail`
     with `Authorization: XBL3.0 x=<uhs>;<xsts token>`, `x-xbl-contract-version: 2`. Titles with a
     `pfn`, `type == "Game"` and the `PC` device are kept (one per package family, case-insensitive);
     `titleHistory.lastTimePlayed` is the last played date (year < 2000 means never).
  6. `POST https://userstats.xboxlive.com/batch` (JSON: `arrangebyfield xuid`, `xuids`, `stats`
     of `MinutesPlayed` per `titleid`, 100 titles per request) gives playtime. Best effort: a
     failure is logged and the library is imported without playtime.
- **Xbox tokens are never stored**: steps 3 and 4 run again for every owned scan (two small
  requests), so only the Microsoft refresh token, the XUID and the gamertag are persisted. The XUID
  is checked to be numeric before it goes into a URL.
- **Owned games use the package family name as id**, the same id as installed games; when an
  installed game matches case-insensitively the installed game's spelling is used so the merge in
  `Library::merge_owned` (exact match) works. The title history lists titles the account has
  played, which includes Game Pass games, not only purchases.
- **Generic addition**: `HttpRequest::post_json` (the Xbox services need JSON bodies); the body is
  treated as a secret for redaction and hidden from `Debug`.
- **The paste fallback accepts the whole address of the blank page** (`oauth20_desktop.srf?code=...`)
  or the bare code; Microsoft codes may contain `*`, `!` and `$`, so Xbox has its own plausibility
  check.


## Ubisoft Connect and Amazon Games (Windows)

- **Ubisoft installs come from `HKLM\SOFTWARE\WOW6432Node\Ubisoft\Launcher\Installs\<id>`**
  (`InstallDir` uses `/` and a trailing slash; normalized). Names: the launcher's product cache,
  then `Uninstall\Uplay Install <id>` `DisplayName`, then the folder name. Launch
  `uplay://launch/<id>/0` (the form Ubisoft's shortcuts use) with `Directory` tracking, since the
  URI starts the launcher first; install `uplay://install/<id>`, uninstall `uplay://uninstall/<id>`
  (the registry's own `UninstallString` runs exactly that). Checked 2026-10-25 with Trackmania (5595).
- **The `configurations` cache is a catalogue, not a library**: protobuf (repeated field 1 =
  `{1: uplay id, 2: install id, 3: YAML}`), 676 products on the maintainer's PC including games he
  doesn't own and DLC. The ownership cache is encrypted and Ubisoft has no sign-in for other
  apps, so uninstalled games come from this catalogue only when the user opts in
  (`providers.ubisoft.importCatalogue`), filtered like Playnite does: `root.start_game` present,
  not `is_ulc`, not another product's `addons` id, no `third_party_platform`, a real name. On the
  maintainer's PC that leaves 26 of 676 products (including Division Beta/PTS test builds, which
  Playnite keeps too). Off by default because it may list games the user doesn't own. Artwork URLs
  are under
  `https://ubistatic3-a.akamaihd.net/orbit/uplay_launcher_3_0/assets/`; thumbnails are 240x280
  (about 6:7), so `covers_are_low_quality` is `true` and SteamGridDB goes first.
- **Amazon on Windows reads the Amazon Games app's SQLite files** in
  `%LOCALAPPDATA%\Amazon Games\Data\Games\Sql\` through `read_foreign`: installed games from
  `GameInstallInfo.sqlite` (`DbSet`: `Id`, `InstallDirectory`, `ProductTitle`, `Installed`), icon and
  backgrounds from `ProductDetails.sqlite` (`game_product_info`, a cache of viewed store pages; no
  portrait art). The id is the Amazon product UUID, the same as Nile's `product.id` on Linux
  (per Playnite; not compared on a machine with both). `Entitlements.sqlite` is DPAPI-encrypted, so
  owned games need a sign-in (below). Launch `amazon-games://play/<id>`, install
  `amazon-games://install/<id>`; the app has no uninstall URI, so Uninstall opens the app.
- **Amazon sign-in is Playnite's launcher flow** (Windows only; Heroic covers Linux): the login
  window opens `www.amazon.com/ap/signin` with the launcher's public device client id, a PKCE S256
  challenge and the launcher's Electron user agent, and catches the return to `www.amazon.com` with
  `openid.oa2.authorization_code`. `api.amazon.com/auth/register` registers the PC as a launcher
  device (serial = Windows `MachineGuid`, so signing in again reuses the device); only the refresh
  token is kept (keyring), `auth/token` refreshes. Owned games: `gaming.amazon.com/api/distribution/
  entitlements` (`GetEntitlements`, paged, Prime "Fuel" loot skipped); its icon and background URLs
  serve as artwork for games the app's cache doesn't know. The verifier is replaced after each
  successful sign-in, so the code-paste fallback and the window share one login URL.
- **Steam sign-in is the store website session** (Playnite does the same): Steam has no sign-in for
  other apps, but every store page of a signed-in user carries a short-lived `webapi_token` that
  `GetOwnedGames` accepts as `access_token` (also for private profiles). The login window for Steam
  is the only one with a persistent profile (`<data>/webview/steam`); a script on store pages
  reports SteamID, token and persona name through a capture navigation to
  `questkeep.invalid/steam-session`. Before each owned scan a hidden, unfocused, unthrottled window
  loads the store with that profile (Steam renews its cookies itself) and reports again, or
  `signedout=1` after 5 s on a signed-out page (the wait lets Steam's renewal redirect finish).
  The core gets that through `auth::WebSession` and keeps only SteamID and name (keyring) and the
  token in memory. Signing out deletes the profile's browsing data. With an API key configured, a
  failing sign-in falls back to the key; the key alone still works as before.

## Tray and autostart

- **Hiding to the tray destroys the main window** rather than hiding it: a hidden WebView2 window
  keeps its renderer (150-250 MB); recreating it takes well under a second and the UI reloads its
  state from the core. The cost is that UI-only state (scroll position, open details) resets.
- **A flag, not window counting, keeps the process alive**: `ExitRequested(code = None)` is
  prevented only while `hidden_to_tray` is set and no tray Exit happened. Closing the window with
  "close to tray" off still quits as before.
- **Tray unavailable means the close button quits**: hiding with no way back would strand the app.
- **Single instance in release builds only**: debug builds skip `tauri-plugin-single-instance` so a
  dev or throwaway instance can run next to an installed one. A second start with `--minimized`
  (autostart racing a manual start) does not raise the window.
- **Autostart runs `--minimized`** and `startMinimized` decides whether that hides the window, so
  the toggle can change without rewriting the registry entry. The entry is written before the
  setting is saved (a refusal is shown and nothing is saved), and refreshed at startup in release
  builds so an updated install path stays correct. Debug builds never touch it.
- **Open folder goes through Rust** (`open_app_folder`) instead of widening `opener` ACL scopes to
  the data directory, which is user-specific and can be portable.
- **Menu rebuilds are debounced (2 s) and skipped when the model is unchanged**, because cover and
  metadata downloads emit `GamesChanged` continuously during the first scan.
- **Tray game icons are made once and cached as 32x32 PNGs, never during a menu build.** A menu
  build then only decodes at most 40 tiny files; producing icons (downloads, exe extraction,
  resizing) happens on the metadata worker and is announced by `GamesChanged`. 32 px stays sharp at
  150-200 % scaling. Items without an icon are plain text items (no placeholder box).
- **Icon sources, best first: store icon, executable icon, cover crop.** The store icon is the
  intended artwork and is free for Steam (local librarycache). The executable icon is what the
  game shows in Explorer, so it beats a cropped box art for `file` games (manual, GOG, Lutris). The
  cover crop (top-aligned: the key art sits at the top of 2:3 covers) is the universal fallback.
  Provider icons must be nearly square, because Epic has no real icon (`Thumbnail` is used when
  square) and a squashed wide logo looks worse than the fallback.
- **Steam icons have no CDN fallback**: the icon's file name is a hash only the client knows.
- **No SteamGridDB for icons**: it would add rate-limited requests for 30 small images; the
  fallbacks are good enough.
- **`image` with only png/jpeg/ico** instead of hand-written decoding/resizing: Lanczos3 resampling
  and robust decoders are not worth re-implementing, and the features keep the dependency small
  (no WebP/GIF/AVIF; those sources fall through to the next one).
- **Events go to the `main` window only** (`emit_to`), so the login windows never receive them.
- **Monochrome tray glyph following the taskbar theme** (`SystemUsesLightTheme`, not the app
  theme): white on dark taskbars, black on light ones, no tile so it fills the tray slot. A thread
  blocks in `RegNotifyChangeKeyValue` to swap it; one of the few `unsafe` modules (scoped
  `allow(unsafe_code)` in `tray_theme.rs`), because winreg cannot wait for changes and polling
  would wake the idle tray process.
- **Window placement in `window.json` in the data folder**, not via `tauri-plugin-window-state`,
  which saves to the app config dir and so would break portable mode. The last normal rectangle is
  tracked on move/resize (a minimized window reports an off-screen position) and saved before the
  window is destroyed or the app exits; it is used only if enough of the title bar is still on a
  connected monitor.
- **Custom tray popup instead of the context menu on Windows.** Native menus cannot be padded,
  show icons only at 16-20 px (scaled with nearest neighbor, so they alias) and cannot show cover
  art. A webview popup would cost 100+ MB and a cold start per opening, so the popup is plain Win32
  + Direct2D (`windows` crate, already in the lockfile through Tauri): instant, and nothing exists
  while it is closed. It is the third place with `unsafe` code (`tray_popup/{render,window}.rs`, scoped
  `allow`); layout and navigation are pure Rust with tests. Its colors mirror `theme.css` (dark
  only, like the app). No acrylic backdrop. Linux keeps the native menu (AppIndicator menus cannot be replaced there).
- **Tray popup accessibility through AccessKit** (MIT/Apache, `accesskit_windows` -> UI
  Automation), not a hand-written UIA provider: the tree is built from the same `Layout` the
  renderer draws (`tray_popup/a11y.rs`, platform independent), so a later Linux popup could expose
  it through `accesskit_unix` (AT-SPI) unchanged. Considered and rejected: a webview popup (best
  accessibility, but 100+ MB and a cold start per opening), egui (GPU context, restyling) and Slint
  (licence needs attribution). A Linux popup is blocked less by drawing than by the tray: the
  AppIndicator backend reports no clicks (tray-icon's KSNI backend would) and Wayland apps cannot
  place a window next to the tray.

- **Provider settings reach providers through `LibraryProvider::configure`**, called with
  `providers.<id>` before every scan (scans already store play actions). First user: GOG's
  `launchThroughGalaxy` (default off: direct launch also works for offline-installer games); the
  UI rescans GOG after the toggle changes so existing games switch immediately.
- **Icons cut from a cover follow the cover**: such icons are marked (`extra.iconFromCover`) and
  dropped when the cover is replaced (manually or by a SteamGridDB re-fetch); the tray queues a new
  one. Store and executable icons are kept. A finished icon job leaves the "already queued" set, so
  a dropped icon can be made again in the same run.
- **A second start of a different executable is announced** in the running instance (toast via a
  queued notice, `take_notices`): with close-to-tray on, an old build waiting in the tray otherwise
  silently swallows starts of a newer build.

- **Custom title bar (`decorations: false`)** drawn by `TitleBar.tsx`; the native shadow and
  resize edges stay. Its caption buttons are out of the tab order like native ones (Win+Up/Down,
  Alt+F4 remain the keyboard paths). Windows 11 Snap Layouts on hover over maximize is lost for now.
- **Each provider ships its own logo** (`LibraryProvider::icon_svg`, files in
  `providers/icons/`, sent as `ProviderInfo.icon`) instead of the UI mapping ids to an icon
  package: a new provider brings its logo with it. The markup is compiled in, so the UI inserts it
  with `innerHTML`; sources without a provider fall back to a generic glyph.
- **Providers can offer extra ways to add games** (`add_game_options`, a split "Add game" button).
  After one runs, a worker scans that provider every 5 s for up to 10 min and imports the first new
  game, so nothing has to be synced by hand.
- **Prism Launcher's "Add Instance" is opened with Ctrl+N**: Prism has no command-line option for
  it. Questkeep starts Prism (`--show-window`, allowed to take the foreground) and sends Ctrl+N only
  once a `prismlauncher.exe` window titled "Prism Launcher…" is in front, so the keys never reach
  another program. Instances play through `--launch <id>`, tracked by the Java process name, since
  Prism hands the launch to its running window and exits.
- **Battle.net reads the agent's `product.db`** (protobuf, a minimal reader in the provider) for
  installs and their "installed" flag (downloads in progress are skipped), and `aggregate.json` for
  names, the `battlenet://` launch URI and box art.
- **EA app games come from the Windows "Apps" list** (entries uninstalled by EA's `Cleanup.exe`)
  and each game's `__Installer\installerdata.xml` (content id, title, launcher path). They start
  through their executable and are tracked by install folder, as the EA app may relaunch them.
- **Battle.net and EA sign in through their websites, like Steam** (`auth::WebAccount`): a login
  window with a persistent profile per store, then a hidden window whose page script reports what
  the scan needs through a capture navigation. Battle.net: the account site's `/api/games-and-subs`
  (Playnite's source); `titleId` is the product's four-letter code as a number, mapped to install
  product codes (`WTCG` → `hsb`). EA: the EA app's own login needs a hardware signature
  (`pc_sign`), so the website login is used, and `connect/auth` for the `ORIGIN_JS_SDK` client with
  `prompt=none` hands that session a token for EA's GraphQL service (the approach Lutris uses; only
  the public endpoints were taken over, no code). Owned EA games keep their content id, or the
  install's id when its manifest lists that content id.
- **One settings list per store** ("Stores and accounts"): sign-in, Steam's API key (shown
  instead of the sign-in, never both), store options and a sync icon button live in the store's
  row; the separate library and Steam sections are gone. Sync results arrive as the usual sync
  toast.
- **Library views live in the database** (`views`, `view_sections`, migration 3), not in
  localStorage: a view is a saved `GameQuery` plus layout, and the sidebar shows only views. The
  keyword filter ("Filter this view…") is never saved with a view and is cleared when another view
  opens; unsaved changes are kept per view as an in-memory draft until the app closes (orange dot).
  The old localStorage layout becomes "All games"'s layout once.
- **The title bar holds the app's actions** (Questkeep menu, Add game, Open launcher, Sync,
  Settings) and a command bar that finds any game regardless of the open view. Last sync times are
  stored (`sync_times`) so the sync popup can show them after a restart. Stores open their own
  launcher through `LibraryProvider::launcher`.
- **Categories are n:m, and store categories map onto them** (migrations 4 and 5). A store's own
  tags are stored as the store reports them (`game_tags`) and reach Questkeep categories through
  `category_sources` (store + name -> category); `game_categories` holds the user's links and, with
  `excluded`, imported categories the user took off a game (those stay off). So merging, separating
  and renaming only move mappings, and a sync never touches the user's choices. Unmapped store
  names go to the category of the same name, created at the end of the list when missing; a
  category left with no mapping and no user games after a sync is removed. Steam collections
  (cloud-storage JSON, `sharedconfig.vdf` tags as fallback), GOG Galaxy tags and Lutris categories
  are imported (`LibraryProvider::scan_categories`; `None` keeps the old tags).
- **Categories have a user order** (`position`), used by grouping, filters and the picker.
- **Grouping is part of a view** (None, Category, Store), saved with it and kept in drafts. A game
  with several categories shows once per group; the keyboard cursor walks slots (game + group), not
  games. Collapsed groups are remembered per view until the app closes. The filter value `:none`
  means "No category".
- **A game in several stores is one entry with copies** (migration 6). Each store's copy keeps
  its own row, so syncs, installs and tracked playtime stay per store; combined copies point at
  the entry's row (`merged_into`, never a chain) and `copy_position` orders them. The library
  reads `library_entries` (entries only; installed, playtime and last played over all copies),
  and store filters and grouping by store see every copy. The entry keeps its name, cover and
  details; favorites and categories carry over. Play starts the first installed copy (a menu
  picks another store); separating a copy remembers the pair so it isn't suggested again.
- **Duplicates are suggested, never combined automatically**: same name ignoring case and
  symbols ("Rocket League®" = "Rocket League"), never two copies from one store in a group. After
  each sync a toast points out new suggestions; the review dialog combines or dismisses them.
